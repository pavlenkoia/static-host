# План: собственные домены и multi-user

[Навигация](../README.md) · [Текущая архитектура](../architecture.md)

Собственные домены реализуются отдельно от multi-user; актуальные контракты описаны в [конфигурации](../reference/configuration.md), [MCP](../reference/mcp.md) и [развёртывании](../operations/deployment.md). Ниже сохранены исходные проектные решения, а не описание текущей реализации. Scopes и multi-user вход не реализованы.

## Будущая модель авторизации

Сущности:

- `users`: владельцы сайтов;
- `agents`: отдельные отзываемые credentials пользователя и ограничения доступа;
- `sites`: владелец, системный ID, текущий каталог, generation и настройки;
- `uploads`: временные загрузки с ограничениями и состоянием;
- `domains`: глобально уникальный hostname, сайт, DNS- и TLS-статус;
- `audit_events`: действия пользователей и агентов без секретов и истории содержимого.

Агенту можно выдать доступ ко всем либо выбранным сайтам владельца и отдельные разрешения на чтение, публикацию и домены. `owner_id` определяется сервером по авторизации; входной site_id не является доказательством доступа. Все операции, включая upload и domains, проверяют владельца и scope.

Предлагается remote MCP через Streamable HTTP. Для локального этапа поддерживаются отзыв, удаление, срок действия и повторное раскрытие новых ключей владельцу. Проверка MCP использует хеш; зашифрованное значение хранится отдельно. Для будущей публичной системы способ входа, выдачу credentials и совместимость со стандартной MCP HTTP authorization потребуется определить отдельно.

## Привязка доменов
### CNAME — основной путь

Сайт имеет несколько доменов и системный адрес; каждый обслуживает одно содержимое без междоменных перенаправлений. Переключатель основного домена не предусмотрен.


Пример: `www.example.com CNAME s-7k3m9.sites.uc.afbmarket.ru`.

Сервис проверяет CNAME-привязку к системному адресу именно выбранного сайта, глобальную уникальность hostname и направление трафика на ingress, затем настраивает маршрут и сертификат. Общий CNAME на ingress без указания сайта не даёт такой же привязки к владельцу.

### A/AAAA — альтернативный путь

Для корня домена допускается A на публичный IPv4 ingress, AAAA — только при реально работающем IPv6. ALIAS/ANAME и flattening обычно видны сервису как итоговые IP и проверяются по модели IP, не CNAME. DNS не должен направлять часть запросов на посторонние адреса.

Принятый риск: совпадение IP подтверждает направление трафика, но не право конкретного пользователя управлять доменом. Другой пользователь может первым заявить ещё не прикреплённый домен, уже указывающий на общий edge. Это осознанное упрощение вместо TXT-проверки; его нельзя описывать как доказательство владения.

Ограничения: один hostname на один сайт во всём сервисе; никакого автоматического переноса между владельцами; конфликт разрешается текущим владельцем или администратором. Пользовательские wildcard-домены не входят в начальный объём. Удалённый/неизвестный hostname не обслуживает прежний или случайный сайт.

DNS proxy, скрывающий origin CNAME/IP, не поддерживается: проверка требует прямого DNS на разрешённые ingress IP.

### DNS и TLS lifecycle

`pending_dns → provisioning_tls → active`; ошибки выпуска видны отдельно и допускают повтор после исправления. Active означает проверенную доступность по HTTPS, а не только запись в БД. Удаление привязки немедленно прекращает отдачу сайта приложением, независимо от наличия сертификата в Caddy.

Для системных hostname уже используется wildcard TLS. Датированный результат его проверки находится в [истории инфраструктуры](../history/infrastructure.md), а порядок настройки — в [развёртывании](../operations/deployment.md). Это отдельный механизм, не реализация собственных доменов.

Для пользовательских доменов выбран On-Demand TLS с обязательным `ask` endpoint. Общий ingress получает fallback-маршрут для hostname, не обслуживаемых явными маршрутами других сервисов. Пользователь согласовал такой общий fallback; существующие явно объявленные домены должны сохранять приоритет. Зарезервированные управляющие адреса и домены других сервисов нельзя привязывать к пользовательским сайтам.

Однократная конфигурация через штатные механизмы Uncloud:

- В глобальной конфигурации Caddy задаётся `on_demand_tls` с внутренним URL `ask` приложения. Endpoint доступен только по внутренней сети, возвращает разрешение только для зарегистрированных, включённых и прошедших DNS-проверку доменов; неизвестные домены и ошибки проверки означают отказ. Не выполнять DNS-проверки синхронно при TLS handshake: endpoint читает подготовленное состояние из БД.
- В Compose `static-host` используется `x-caddy`: явные маршруты кабинета/MCP/upload и fallback HTTPS с `tls { on_demand }`, проксирующий в `{{upstreams <port>}}`. HTTP/HTTPS-публикации через `x-ports` с `x-caddy` у одного сервиса не совмещаются. Обработка HTTP и ACME challenge также должна быть проверена в общей конфигурации.
- Глобальные параметры вносятся в управляемый источник конфигурации Caddy, не в сгенерированный файл. Поддержка необходимых механизмов подтверждена по исходникам установленного Uncloud 0.21.0; поведение маршрутов и On-Demand TLS проверено изолированно на Caddy 2.11.7. Итоговая production-конфигурация и публичный ACME ещё не проверены.

Добавление домена меняет только состояние приложения: DNS и уникальность проверяются заранее, затем Caddy получает разрешение из БД и выпускает сертификат при первом TLS handshake. Готовность HTTPS проверяется до перехода в `active`; диагностика доступна через кабинет и MCP. Ни `uc deploy`, ни перезагрузка Caddy для каждого нового домена не нужны.

`ask` ограничивает управление сертификатами, а не авторизует каждый HTTP-запрос и не гарантирует мгновенный отзыв уже выпущенного сертификата. Приложение проверяет hostname при каждой отдаче сайта и отказывает для неизвестных или отключённых привязок. Неограниченный On-Demand TLS запрещён. Изменение файлов сайта не меняет ingress-конфигурацию.

## Остальные открытые вопросы

- Публичный multi-user вход, выдача credentials и совместимость MCP HTTP authorization.
- Квоты и rate limits многопользовательского сервиса, хранение аудита.
- Политика поддержки DNS proxy и способы доказательства владения для будущего multi-user.

Проверка совместимости механизма не является реализацией: [историческое исследование](../history/infrastructure.md).
