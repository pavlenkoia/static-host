## Развёртывание поддержки собственных доменов: 2026-11-26

На `uc-1` запущен локально собранный образ `static-host:domains-20261126-healthfix`, а на `edge-1` настроен внутренний Caddy ask. Перед миграцией создана защищённая копия каталога данных вне ноды; SQLite `quick_check` прошёл, восстановление не проверялось. Первая попытка обновления вызвала простой: healthcheck использовал неверный Host, а старая версия не запускалась на схеме v6. Исправленный образ восстановил сервис без отката данных.

После обновления оба контейнера healthy, HTTPS панели и существующего опубликованного сайта вернул 200, MCP без ключа — 401, `/.uncloud-verify` — 200. HTTP fallback перенаправляет на тот же hostname, ask отказывает неизвестному домену, Caddy не выдаёт ему HTTPS. Привязка настоящего собственного домена и публичный ACME пока не проверены. Образ передан на ноду напрямую и ещё не опубликован в registry.

## Результат: 2026-11-25

В проектной памяти зафиксированы развёртывание приложения на `uc-1` и публичный wildcard ingress на `edge-1`: Caddy 2.11.7 с Cloudflare v0.2.4, доверенный wildcard TLS и сквозная цепочка MCP create → HTTPS upload → publish → точное содержимое сайта. Управляющие endpoints на hostname сайта возвращали 404; временные сайт, ключ и сессия были удалены. Собственные домены и On-Demand TLS не включались.

Основания: `.llm-wiki/sources/first-deploy.md`, `.llm-wiki/sources/wildcard-ingress.md`. Это более позднее состояние, чем первоначальное исследование ниже.

## Изолированная проверка будущих динамических доменов, 2026-11-25

Production использовался только для чтения: `uc version`, `uc machine ls`, `uc inspect caddy`, `uc caddy config`, `uc exec -T caddy caddy version`. На обеих нодах подтверждён Uncloud 0.21.0; работающий Caddy — 2.11.7, build hash `h1:yj0Y4fYZGPkSvibBJ1sTWE33xC0fxztVyXEW5iIdUT4=`.

Исходники тега Uncloud `v0.21.0` (commit `c58108aa829cca4fe3b5f837e0f1918be1687599`, совпадает с CLI) подтверждают поддержку глобального конфига из Caddy-сервиса, `x-caddy`, шаблонов `upstreams` и запрет совмещения `x-caddy` с ingress `x-ports`. Проверены `internal/machine/caddyconfig/caddyfile.go`, `template.go` и `pkg/client/compose/service.go`.

Локально запущен отдельный контейнер `caddy:2.11.7` с теми же версией и build hash, без подключения production-хранилищ. Тестовый HTTP backend имитировал разрешённые домены; сертификаты выпускались внутренним CA (`tls internal`), не публичным ACME. `caddy adapt --validate` принял объединённую конфигурацию: глобальный `ask`, явные hostname и HTTPS catch-all. Runtime-проверки прошли:

- явные маршруты другого сервиса и панели имеют приоритет над fallback;
- неизвестный домен получает отказ в TLS через `ask`;
- добавленный после старта разрешённый домен получает локальный сертификат и ответ backend без reload;
- после удаления разрешения backend возвращает 404 даже при сохранённом сертификате;
- HTTP endpoint `/.uncloud-verify` остаётся доступен.

Обновление Uncloud ради этих механизмов не требуется. Это не проверка готового production-развёртывания: публичный ACME/Let's Encrypt, DNS, wildcard TLS, доступность будущего `ask` между нодами, итоговый Compose через реальный deploy и HTTPS readiness приложения не проверялись. Приложение и endpoint ещё не реализованы. Конфигурация Caddy, DNS и сервисы production не менялись; временный локальный контейнер остановлен.

## Первоначальные наблюдения кластера, 2026-11-25

Эти наблюдения предшествовали развёртыванию и wildcard ingress; утверждения об отсутствии проверок и ещё не выбранной ноде относятся только к этому снимку.

Снимок исследования 2026-11-25; не гарантия актуального состояния:

- Uncloud CLI и машины — 0.21.0; edge-1 и uc-1 доступны.
- edge-1 имеет публичный IP, 1 CPU, около 1 ГБ RAM и около 11 ГБ свободного диска.
- uc-1 не показывает публичный IP; его CPU/RAM/диск не исследованы.
- Единственный сервис Uncloud — healthy Caddy `caddy:2.11.7` на edge-1. Uncloud volumes отсутствуют.
- Настроенный домен Uncloud был `uc.tiangroup.su`; выбор `uc.afbmarket.ru` — проектное решение, не выполненное изменение DNS/кластера.
- Wildcard DNS, DNS-provider API и наличие нужного Caddy-модуля не проверены.

`edge-1` остаётся публичным прокси с Caddy. `static-host` запускается на рабочей ноде и принципиально закрепляется за ней: SQLite, ключ шифрования и файлы сайтов находятся в подключённом постоянном каталоге этой ноды. `uc-1` — кандидат, его ресурсы ещё требуется проверить. Caddy обращается к контейнеру через внутреннюю сеть Uncloud; публичный IP приложению не нужен. Автоматический перенос приложения и данных не предполагается. Это размещение без HA; сборки на малом edge не выполняются.
