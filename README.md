# static-host

Статус: single-owner кабинет, MCP и публикация готовых статических сайтов реализованы. В текущей установке Uncloud настроен публичный wildcard ingress системных сайтов с TLS; собственные домены не поддерживаются.

## Запуск

Требуются GNU Make, Go 1.27.4 или новее, Node.js 24 и свободный порт 8081. Для разработки создайте корневой `.env` и задайте в нём `STATIC_HOST_ADMIN_PASSWORD` длиной 12–72 байта:

```sh
cp .env.examples .env
chmod 600 .env
# Отредактируйте .env и задайте пароль, затем:
make dev
```

`make dev` загружает `.env` в окружение, устанавливает зависимости из lockfile, собирает интерфейс и запускает Go-сервер. Файл читается как shell-файл: значения с пробелами, `$` или `#` заключайте в одинарные кавычки; не помещайте в него команды. Не коммитьте `.env`. В dev базовый домен принудительно отключён, поэтому значения домена и ноды для Compose не мешают локальному входу. Адрес и каталог данных можно задать в `.env` через `STATIC_HOST_LISTEN` и `STATIC_HOST_DATA_DIR` (по умолчанию `127.0.0.1:8081` и `./data`). Остановка — Ctrl+C. Сам Go-бинарник `.env` автоматически не читает.

`STATIC_HOST_ADMIN_PASSWORD` обязателен при каждом запуске сервера и должен содержать 12–72 байта. Единственный логин — `admin`. Пароль считывается из окружения во время работы и не сохраняется в SQLite или журналах. При следующем запуске принимается пароль из нового окружения. Каждый запуск очищает браузерные сессии, сохраняя ключи агентов MCP и материалы их шифрования. Команд bootstrap/reset владельца нет.

Кабинет доступен на `http://127.0.0.1:8081/`. Новые ключи по умолчанию бессрочные; можно задать срок в днях, повторно показать или скопировать значение, отозвать или удалить ключ. Ключ даёт полный доступ агента к MCP по `Authorization: Bearer <ключ>` на `/mcp`; отзыв и удаление действуют на следующий запрос. Значения старых ключей, выпущенных до поддержки повторного просмотра, восстановить нельзя.
Агент вызывает `sites_create`, затем `uploads_create` с текущим `expected_generation`, отправляет ZIP или tar.gz по выданному URL методом PUT с тем же bearer-ключом и указанным Content-Type, затем вызывает `sites_publish` с `upload_id` и уникальным `idempotency_key`. Архив должен содержать непустой `index.html` в корне. Каждая публикация полностью заменяет файлы сайта; исходники и восстановление старого содержимого остаются у владельца. `sites_list`, `sites_get` и `sites_delete` доступны агенту; кабинет показывает сайты и позволяет безвозвратно их удалять.

Лимиты: 100 сайтов, один активный upload, архив до 100 МиБ, распакованное содержимое до 250 МиБ и 10 000 файлов, общий опубликованный объём 5 ГиБ. Upload URL действует 15 минут и содержит секретную capability; не публикуйте его. Локальные адреса имеют вид `http://<site-id>.localhost:8081/` с настроенным портом. Собственные домены, SPA fallback, история и rollback в локальной реализации не поддерживаются.

Новые значения ключей зашифрованы в SQLite с помощью AES-256-GCM. Файл `agent-key-encryption.key` в каталоге данных необходим для их восстановления: храните и резервируйте его вместе с БД, не раскрывайте и сохраняйте права 0600. Процесс с доступом к обоим файлам может прочитать ключи; это не защита при полном захвате сервера.

SDK Go v1.8.0: при протоколе по умолчанию `2026-07-28` его `ClientSession.Ping` не добавляет обязательные метаданные и получает 400; для этого клиента можно явно выбрать `ClientSessionOptions{ProtocolVersion: "2025-11-25"}`. Поддержка версий сервером не ограничена.

Интерфейс собирается из общих Vue-примитивов в `web/src/components/ui/` с утилитами Tailwind CSS; семантические токены темы определены в `web/src/style.css`.
Настройки: `--listen` / `STATIC_HOST_LISTEN` (по умолчанию `127.0.0.1:8081`), `--data-dir` / `STATIC_HOST_DATA_DIR` (`./data`), `--base-domain` / `STATIC_HOST_BASE_DOMAIN` (пусто). Явный флаг имеет приоритет над окружением. Без домена разрешён числовой loopback или wildcard (`0.0.0.0` / `::`); по умолчанию для wildcard origin остаётся loopback. Для доступа из доверенной сети задайте `--local-origin http://<IP-сервера>:<порт>` либо `STATIC_HOST_LOCAL_ORIGIN`; порт должен совпадать с listener, IP должен быть числовым. Принимается только указанный Host и Origin. HTTP не шифрует пароль и ключи; не используйте этот режим в недоверенной сети. Системные адреса сайтов остаются на `.localhost` и с другого устройства не указывают на сервер. При заданном домене кабинет доступен по `https://panel.<домен>`, MCP — по `https://mcp.<домен>/mcp`, загрузка — по `https://upload.<домен>`, системные сайты — по `https://<site-id>.sites.<домен>`. TLS завершает внешний прокси с сохранением Host. Compose объявляет только явные маршруты панели, MCP и upload; DNS и wildcard ingress/TLS сайтов приложением не настраиваются.

Проверка состояния:

```sh
curl --noproxy '*' http://127.0.0.1:8081/healthz
```

Ответ: `ok` и перевод строки. Остановить сервер можно с помощью Ctrl+C или SIGTERM.

## Контейнер и Uncloud

Образ собирается для `linux/amd64`: `docker build -t static-host:smoke .`, затем `bash scripts/container-smoke.sh static-host:smoke`. Smoke использует временные Docker volumes и не затрагивает `./data`. Образ работает от UID/GID 10001, хранит данные в `/data` и слушает `0.0.0.0:8081`; для запуска сервера требуется `STATIC_HOST_BASE_DOMAIN`. Listener можно переопределить через `STATIC_HOST_LISTEN`.

`compose.yaml` предназначен для одного экземпляра на выбранной ноде Uncloud. Скопируйте `.env.examples` в `.env`, задайте свои `STATIC_HOST_BASE_DOMAIN`, `STATIC_HOST_MACHINE` и `STATIC_HOST_ADMIN_PASSWORD`. Compose требует пароль через обязательную интерполяцию; пример оставляет секрет пустым намеренно, его нужно заменить. Выбирайте случайный секрет длиной 12–72 байта. Защитите `.env` правами доступа и не добавляйте его в систему контроля версий. Передача пароля через переменную окружения означает, что привилегированный пользователь Docker может увидеть его в `docker inspect`; ограничьте доступ к Docker daemon и рабочей ноде. Не передавайте пароль в командной строке. Образ и каталог данных `/var/lib/static-host` заданы в Compose. Caddy получает только маршруты `panel.<домен>` и `mcp.<домен>`; DNS, TLS и глобальная конфигурация Caddy здесь не меняются. Обновление stop-first допускает простой; не запускайте две копии с одной SQLite.

На выбранной ноде создайте **новый** каталог данных с владельцем `10001:10001` и правами `0700`: `sudo install -d -m 0700 -o 10001 -g 10001 /var/lib/static-host`. Не применяйте эту команду к существующему произвольному каталогу; для существующих данных сохраняйте текущие права и владельца. При первом старте приложение автоматически создаёт состояние администратора. Последующие старты используют новый пароль из окружения; старый пароль перестаёт работать, браузерные сессии инвалидируются, а ключи агентов и `agent-key-encryption.key` сохраняются. Резервируйте SQLite и `agent-key-encryption.key` вместе вне ноды и проверяйте восстановление.

После подготовки и отдельного разрешения на развёртывание: `uc deploy -f compose.yaml --no-build`. Это не настраивает DNS или глобальный Caddy и не проверяет доступность кластера.

### Системные сайты: wildcard ingress

`compose.yaml` маршрутизирует `*.sites.${STATIC_HOST_BASE_DOMAIN}` на приложение. Для этой зоны нужны wildcard DNS на публичный ingress и Caddy с модулем Cloudflare; обычный образ Caddy не подходит. Собственные домены и On-Demand TLS этим не включаются.

Сборка и доставка Caddy на публичную ноду:

```sh
docker build -t static-host-caddy:2.11.7-cloudflare-0.2.4 deploy/caddy
uc image push static-host-caddy:2.11.7-cloudflare-0.2.4 -m edge-1
uc caddy deploy --image static-host-caddy:2.11.7-cloudflare-0.2.4 -m edge-1
```

Перед обновлением Caddy установите Cloudflare API-токен в `/var/lib/uncloud/caddy/cloudflare-api-token` на edge-1: владелец root, права 0600. Токен должен иметь Zone:DNS:Edit и Zone:Zone:Read только для нужной зоны. Entrypoint читает файл через существующий bind mount `/etc/caddy` и передаёт токен процессу Caddy через окружение; значение не включается в образ, Compose или генерируемый Caddyfile. Не выводите окружение процесса и не коммитьте секрет. Этот файл нужен при каждом запуске Caddy и для автоматического продления сертификата.

Обновление приложения выполняйте с Compose override, закрепляющим `services.static-host.image` по digest опубликованного выпуска: `uc deploy -f compose.yaml -f /путь/release.yaml --no-build --yes`. Uncloud может использовать закэшированный `latest` без загрузки нового образа. Перед применением wildcard-маршрута сначала обновите Caddy; сохраните существующий глобальный Caddyfile через `--caddyfile`, если он настроен. Не редактируйте генерируемый Caddyfile. Проверяйте trusted HTTPS реального опубликованного сайта, а не только health приложения.

Workflow **Container image** запускается только вручную: GitHub → Actions → Container image → Run workflow → ветка `main` (либо `gh workflow run image.yml --ref main`). На push и PR образ не собирается; при выборе другой ветки job пропускается. Выпуск выполняет `make check-fast`, сборку и smoke, затем публикует в GHCR теги `sha-<полный SHA>` и `latest`. Deploy не выполняется. После первой публикации владелец должен один раз выбрать package → **Change visibility → Public**, затем подтвердить публичность анонимным `docker pull ghcr.io/<owner>/<repo>:<tag>` без сохранённой авторизации. Публикация сама по себе не подтверждает публичную видимость.

## Обязательные проверки разработки

Перед завершением каждого изменения выполните из корня репозитория:

```sh
make check-fast
```

Команда устанавливает зависимости из lockfile, собирает интерфейс и выполняет `go test -race -count=1 ./...`. Для изменений интерфейса дополнительно выполните полный gate:

```sh
make check
```

Он также устанавливает Chromium и запускает браузерные тесты Playwright. Требуются GNU Make, Go и Node.js указанных выше версий, C toolchain для Go race detector; для браузерных тестов — системные библиотеки Chromium. На Linux их можно установить один раз: `npm --prefix web ci && npm --prefix web exec -- playwright install-deps chromium` (может потребоваться sudo). Любая ошибка останавливает проверку; пропуски и retries не используются.

Backend-тесты проверяют авторизацию, сессии, ключи агентов, SQLite/миграции, MCP и запуск CLI. Браузерные тесты проходят пользовательские сценарии на настоящем Go-сервере со свежей временной БД, не используя рабочий `./data` или сервер на 8081. При изменении поведения обновляйте соответствующие тесты; исправления непокрытых ошибок сопровождайте regression test.

Для узкой проверки после установки зависимостей и сборки интерфейса: `go test ./internal/web` либо `npm --prefix web test`. Это не заменяет соответствующий итоговый gate.

Workflow **Checks** запускает `make check-fast` только на pull request, не на push. При ручном выпуске образа `make check-fast` также выполняется перед сборкой. Браузерные тесты выполняются только локально через `make check`; в GitHub Actions они не запускаются. Чтобы запретить слияние без быстрой проверки, в ruleset/защите основной ветки необходимо сделать статус **Required checks** обязательным и требовать pull request. Workflow сам не изменяет настройки защиты репозитория.

Подробности и планируемая архитектура — в [docs/architecture.md](docs/architecture.md).
