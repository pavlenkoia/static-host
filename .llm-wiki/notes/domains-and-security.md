# Домены и безопасность

Базовый домен задаётся установкой; `uc.afbmarket.ru` — исторический пример, не default. При заданном домене кабинет и MCP доступны на HTTPS `panel.<домен>` и `mcp.<домен>`. Адреса upload и сайтов пока не реализованы. Site-id генерируется сервером и не переиспользуется. Выбор домена не означает выполненную настройку DNS.

Свои домены подключаются без отдельной TXT-проверки. Основной путь: CNAME на системный адрес конкретного сайта. Сервис проверяет соответствие выбранному сайту, уникальность hostname, направление трафика и готовность HTTPS.

Для корневого домена допустим A/AAAA на разрешённые адреса ingress; AAAA только при работающем IPv6. Flattening/ALIAS обычно проверяется как IP. Принятый риск: совпадение IP не подтверждает право пользователя на домен. Другой пользователь может первым заявить незакреплённый домен, уже указывающий на общий edge. Не называть эту проверку доказательством владения.

Hostname глобально уникален; автоматического переноса между владельцами нет. Неизвестные и отключённые hostname не обслуживают случайный или старый сайт. Пользовательские wildcard-домены не входят в начальный объём. Поддержка скрывающего origin DNS proxy ещё не определена.

Lifecycle: pending_dns → provisioning_tls → active; active требует проверенной доступности HTTPS, ошибки TLS видны пользователю. Системному wildcard TLS нужен DNS challenge и совместимый Caddy-модуль.

Для своих доменов выбран On-Demand TLS с обязательным внутренним `ask` endpoint приложения. В общем Caddy один раз задаётся fallback для hostname вне явных маршрутов остальных сервисов; такой fallback согласован владельцем. Явные маршруты других сервисов сохраняют приоритет, их домены и управляющие hostname нельзя привязывать к сайтам. Глобальный `on_demand_tls`/`ask` задаётся в управляемой конфигурации Caddy; `x-caddy` сервиса задаёт маршруты и upstream. HTTP/HTTPS `x-ports` с ним не совмещается. Генерируемый Caddyfile не редактируется.

Добавление домена меняет только БД: DNS и уникальность проверяются заранее, `ask` читает подготовленное разрешение и отказывает для неизвестных, отключённых доменов и при ошибках. Caddy выпускает сертификат при первом handshake, хранит и продлевает его. Ни деплой сервиса, ни reload Caddy на каждый домен не нужны. `ask` не авторизует каждый HTTP-запрос: после удаления привязки приложение немедленно прекращает отдачу сайта, независимо от сохранённого сертификата. Неограниченный on-demand запрещён. Привилегированный domain-controller не требуется.

Реализации в production ещё нет. [Проверка совместимости](/sources/domain-compatibility.md) подтвердила поддержку по исходникам Uncloud 0.21.0 и runtime-тесту Caddy 2.11.7 той же сборки: явные маршруты имеют приоритет; `ask` запрещает неизвестные домены; новый разрешённый домен получает локальный сертификат без reload; удалённый домен не отдаёт сайт при сохранённом сертификате; HTTP endpoint Uncloud работает. Обновление Uncloud для механизма не требуется. Тест использовал внутренний CA и имитацию backend. Публичный ACME, DNS, wildcard TLS, межнодовая сеть `ask`, итоговый deploy, HTTPS readiness и диагностика приложения ещё не проверены. Основание решения: [динамические домены и размещение](/sources/dynamic-domains.md).

Пользовательский HTML изолирован от управляющих hostname. Все поддомены всё ещё имеют общую site-границу afbmarket.ru: host-only __Host- cookies, CSRF и Origin checks обязательны; общие domain cookies недопустимы. Upload требует лимитов, безопасной распаковки, квот и проверки прав. Секреты не сохранять в документации/wiki.
