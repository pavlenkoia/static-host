# Динамические домены и размещение сервиса

> Source: `raw/2026-11-25-dynamic-domains.md`

Принятое решение: `edge-1` остаётся публичным Caddy-прокси, `static-host` закрепляется за рабочей нодой с постоянными данными. Для пользовательских доменов используется общий fallback в Caddy и On-Demand TLS с обязательным внутренним `ask` endpoint приложения. Явные маршруты остальных сервисов сохраняют приоритет; их домены нельзя назначать сайтам.

Глобальный `on_demand_tls`/`ask` и `x-caddy` сервиса настраиваются один раз через Uncloud. Затем добавление домена меняет только БД приложения, без деплоя или перезагрузки Caddy. Привилегированный domain-controller не нужен. Приложение заранее проверяет DNS и уникальность, разрешает управление сертификатом только для включённых проверенных привязок и проверяет hostname при каждой отдаче сайта. `ask` не отзывает уже выпущенный сертификат и не авторизует каждый запрос.

Решение пока не реализовано в production. [Проверка совместимости](/sources/domain-compatibility.md) подтвердила необходимые механизмы по исходникам Uncloud 0.21.0 и изолированному запуску Caddy 2.11.7: приоритет маршрутов, разрешение/отказ через `ask`, новый домен без reload и сохранение HTTP endpoint Uncloud. Использовался внутренний CA. Публичный ACME, DNS, wildcard TLS, межнодовая доступность будущего `ask`, реальный deploy, HTTPS readiness и диагностика приложения остаются непроверенными. Production не изменялся.

Решение заменяет предложения размещать приложение на edge и синхронизировать список доменов привилегированным контроллером. Подробности: [домены и безопасность](/notes/domains-and-security.md), [инфраструктура](/notes/infrastructure-and-workflow.md). Первичные технические ссылки приведены в raw-источнике и `docs/architecture.md`.
